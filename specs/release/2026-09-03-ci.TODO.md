# CI: test automatici + build di release

Stato: proposta, da implementare per la parte di test (nessuna
domanda bloccante); la parte di build/release dipende dalla spec di
firma (`2026-09-03-firma-notarizzazione.TODO.md`) — implementabile a
pezzi, non tutta insieme.

## Motivazione

`.github/workflows/` non esiste: niente gira automaticamente su push
o pull request. Ogni verifica (`cargo test`, `cargo clippy`, `npm run
typecheck`, `npm run test`) è fatta a mano, task per task — funziona
in una sessione di lavoro seguita passo passo, ma non protegge da una
regressione che sfugge a una verifica manuale, né permette a un
collaboratore futuro di sapere se il proprio branch è a posto senza
chiedere.

## Due workflow separati

### 1. `test.yml` — nessuna domanda aperta, implementabile subito

Su ogni push e pull request verso `main`:
- `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo
  fmt --all -- --check` (stessa identica checklist di CLAUDE.md).
- `npm run typecheck`, `npm run test` (vitest).
- Matrice minima: **solo Ubuntu** per questo workflow — i test Rust
  del core sono già cross-platform per costruzione (`tempfile`,
  percorsi via `std::path`), non serve tripla matrice per test unitari
  che non toccano funzionalità OS-specifiche (mobile `cfg(mobile)`,
  ancora non compilato/testato nemmeno localmente su un target reale —
  vedi `specs/release/2026-09-03-verifica-cross-platform.TODO.md`).

### 2. `release.yml` — bloccato sulla spec di firma

Su un tag `v*`: build della matrice macOS/Windows/Linux via
`tauri-apps/tauri-action` (l'action ufficiale, stesso principio di
"solo dipendenze ufficiali" già seguito per i plugin Tauri), upload
degli asset su una GitHub Release. **Non implementabile in modo
sensato prima della spec di firma**: pubblicare build non firmate
automaticamente non risolve nulla, anzi restituisce artefatti che
Gatekeeper/SmartScreen bloccano comunque — l'automazione della build
va di pari passo con la firma, non prima.

## Modifiche

- `.github/workflows/test.yml` (nuovo file) — la parte non bloccata.
- `.github/workflows/release.yml` — scritto ma non attivato
  (nessun trigger reale, o commentato) finché la spec di firma non è
  risolta, per evitare di pubblicare artefatti non firmati per errore.

## Domande aperte

Nessuna per `test.yml`. `release.yml` eredita le domande già aperte
nella spec di firma (credenziali, dove ospitarle come GitHub Actions
secrets).
