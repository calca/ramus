# Multilingua: messaggi d'errore (CoreError strutturato)

Stato: proposta, da implementare **dopo**
`specs/refinement/2026-09-04-i18n-interfaccia.TODO.md` (serve
l'infrastruttura i18next già pronta: dizionari, `t()`, `Locale`).
Ambito confermato dall'utente ("anche i messaggi di errore", non solo
l'interfaccia) — la parte più grande e più rischiosa delle due spec
i18n, documentata qui con precisione perché non è solo "aggiungere
traduzioni", tocca com'è strutturato `CoreError` da cima a fondo.

## Perché è un problema diverso dalle stringhe statiche

Oggi `CoreError` (`crates/ramus-core/src/error.rs`) ha un
`impl Serialize` scritto a mano che manda al frontend **una stringa
già pronta in italiano** (`serializer.serialize_str(&self.to_string())`,
dove `to_string()` usa i messaggi `#[error("...")]` di `thiserror`).
Ogni punto del frontend che cattura un errore lo tratta già come
stringa finale — **17 punti** fanno `String(err)`/`setError(String(err))`
diretto (contato con `grep`, non stimato). Per tradurre serve che il
frontend riceva un **codice** + eventuali **parametri**, non un testo
già composto — cambia la forma dei dati sul filo, non solo cosa c'è
scritto.

In più, **3 delle 9 varianti** (`Config(String)`, e i wrapper
`Index(rusqlite::Error)`/`Search(tantivy::TantivyError)`/
`Git(git2::Error)`) portano un messaggio libero non strutturato:
`Config(String)` è costruita a mano in **27 punti** del codice (quasi
tutti in `src-tauri/src/commands.rs`, per mutex avvelenati — es.
`CoreError::Config("stato di configurazione corrotto".to_string())`)
con testo italiano diverso ogni volta, non riconducibile a un
template fisso. I tre wrapper (`rusqlite`/`tantivy`/`git2`) portano
invece il messaggio **in inglese** dalla libreria di origine — già oggi,
prima di questa spec, non italiano coerente. Tradurre "davvero" questi
casi richiede eliminare il testo libero, non solo aggiungerne la
traduzione.

## Cosa resta in italiano (per scelta, non per limite)

`impl std::error::Error`/`Display` di `CoreError` (i messaggi
`#[error("...")]` di `thiserror`) **non cambia**: restano in italiano,
usati per i log Rust lato server e per `ramus-mcp` (i cui errori
tornano a un client MCP, cioè un agente — non una persona con una
lingua preferita, tradurli lì non avrebbe senso, vedi "Fuori scope"
della spec sorella). Cambia **solo** la serializzazione verso i
comandi Tauri consumati dalla GUI.

## Modifiche

### 1. Varianti a testo libero diventano tipizzate

`CoreError::Config(String)` usato per mutex avvelenati va sostituito
con varianti dedicate senza payload testuale libero, es.:
```rust
#[error("stato di configurazione corrotto")]
PoisonedConfigLock,
#[error("stato dell'indice corrotto")]
PoisonedIndexLock,
#[error("stato dell'indice di ricerca corrotto")]
PoisonedSearchIndexLock,
#[error("stato del watcher corrotto")]
PoisonedWatcherLock,
```
(i nomi esatti da rivedere sui 27 call site reali — non tutti sono
mutex avvelenati, alcuni potrebbero restare `Config(String)` per un
messaggio genuinamente dinamico che non ha senso tipizzare: da
verificare punto per punto in implementazione, non indovinabile da
qui). `Index`/`Search`/`Git` (wrapper di errori di libreria esterna)
**restano com'erano** nella struttura Rust (serve comunque propagare
l'errore originale con `#[from]`) ma il messaggio verso il frontend
diventa un codice generico (`"index_error"`/`"search_error"`/
`"git_error"`) con il messaggio della libreria come parametro
`detail` — tradotto solo il template ("Errore di ricerca: {detail}" /
"Search error: {detail}"), il `detail` stesso resta quello che la
libreria produce (inevitabile: non è testo di Ramus da tradurre).

### 2. Nuova serializzazione: codice + parametri

```rust
impl Serialize for CoreError {
    fn serialize<S: Serializer>(&self, serializer: S) -> Result<S::Ok, S::Error> {
        let mut map = serializer.serialize_map(Some(2))?;
        let (code, params): (&str, serde_json::Value) = match self {
            CoreError::InvalidPath(path) => ("invalid_path", json!({ "path": path })),
            CoreError::PageNotFound(path) => ("page_not_found", json!({ "path": path.display().to_string() })),
            CoreError::InvalidDate(date) => ("invalid_date", json!({ "date": date })),
            CoreError::MalformedBlock { line, reason } => ("malformed_block", json!({ "line": line, "reason": reason })),
            CoreError::Io { path, source } => ("io", json!({ "path": path.display().to_string(), "detail": source.to_string() })),
            CoreError::PoisonedConfigLock => ("poisoned_config_lock", json!({})),
            // ... altre varianti di lock avvelenato
            CoreError::Index(e) => ("index_error", json!({ "detail": e.to_string() })),
            CoreError::Search(e) => ("search_error", json!({ "detail": e.to_string() })),
            CoreError::Git(e) => ("git_error", json!({ "detail": e.to_string() })),
        };
        map.serialize_entry("code", code)?;
        map.serialize_entry("params", &params)?;
        map.end()
    }
}
```
`code` stringhe stabili (usate come chiave di traduzione lato
frontend, es. `errors.invalid_path`) — cambiarle in futuro rompe la
traduzione silenziosamente, vanno trattate come API pubblica fra
Rust e frontend, stesso principio già seguito per gli id di
`SHORTCUT_ACTIONS`.

### 3. Frontend: un solo punto che traduce

Nuovo `src/lib/errors.ts`:
```ts
interface CoreErrorPayload { code: string; params: Record<string, string | number>; }

function isCoreErrorPayload(err: unknown): err is CoreErrorPayload {
  return typeof err === "object" && err !== null && "code" in err && "params" in err;
}

export function translateError(err: unknown): string {
  if (isCoreErrorPayload(err)) {
    return i18next.t(`errors.${err.code}`, err.params);
  }
  return String(err); // errore non-CoreError (JS nativo, Tauri interno): invariato
}
```
Ognuno dei 17 punti `String(err)`/`setError(String(err))` diventa
`translateError(err)` — stesso identico punto di chiamata, cambia solo
la funzione. Chiavi `errors.*` in `it.ts`/`en.ts` (spec sorella),
interpolazione via i18next (`{{path}}`, `{{detail}}`, ecc.) per i
parametri.

## Fuori scope

- Tradurre i messaggi delle librerie esterne (`rusqlite`/`tantivy`/
  `git2`): restano nella lingua che producono loro (inglese), solo il
  template che li introduce è tradotto — vedi sopra.
- Errori di `ramus-mcp`: restano stringhe italiane semplici, nessun
  client MCP (un agente) beneficia da una traduzione — stessa
  scelta già presa nella spec sorella.
- Un sistema generico di errori localizzabili riusabile altrove
  (es. per futuri plugin): non esistono plugin (SPEC.md, "Fuori
  scope"), non c'è nulla da generalizzare oltre `CoreError`.

## Domande aperte

Una, da risolvere **durante** l'implementazione leggendo i 27 call
site uno per uno, non decidibile a priori: quali varianti
`Config(String)` diventano davvero tipizzate (messaggio fisso, un
codice) e quali — se ce ne sono — restano a testo libero perché il
messaggio è intrinsecamente dinamico e non ha un template sensato.
Non blocca l'inizio del lavoro, blocca solo l'ultimo dettaglio.

## Test da scrivere

**Rust**: per ogni variante di `CoreError`, un test che verifica la
serializzazione produca `{"code": "...", "params": {...}}` nella
forma attesa (round-trip-like: costruisci l'errore, serializza,
verifica campi) — stesso principio già seguito per il round-trip del
parser, applicato qui alla forma sul filo invece che al testo su
disco.
**Frontend**: `translateError` — un test per il caso `CoreErrorPayload`
(traduzione con interpolazione) e uno per il caso non-riconosciuto
(fallback a `String(err)`).
