# Impostazioni

Stato: implementata.

## Motivazione

M1 ha già `get_config`/`set_vault_path` lato backend ma nessuna UI: il
vault path può cambiare solo modificando `config.json` a mano. Questa
spec aggiunge una schermata Impostazioni per farlo dall'app, più due
impostazioni aggiuntive (tema, info vault) decise col progettista.

Restano esplicitamente **fuori scope** (M2/M3/M4, non da anticipare):
sync/git, ricerca/indice, configurazione AI, multi-vault. Le
impostazioni qui dentro riguardano solo M1.

## Apertura

Icona (ingranaggio) in `app-header`, apre un pannello modale sopra la
vista journal (overlay + backdrop, chiusura con Escape o click fuori).
Nessuna vista/route separata: coerente con "zero attrito all'avvio",
le impostazioni restano un passo deliberato che non interferisce con
l'apertura automatica del journal.

## Vault: cambio percorso

Selezione tramite dialog nativa di sistema (non un campo di testo):
serve `@tauri-apps/plugin-dialog` lato JS e la crate
`tauri-plugin-dialog` lato Rust — unica dipendenza nuova di questa
spec, motivata dal fatto che un campo di testo per un percorso
filesystem è un'esperienza scadente e a rischio di errori rispetto a
un selettore nativo, e non esiste un'alternativa senza plugin (il
webview non ha accesso al filesystem nativo).

**Nessuno spostamento file.** Scegliere una cartella diversa fa
semplicemente puntare l'app lì: se è vuota (o non esiste) diventa un
vault nuovo (stessa creazione automatica di `journals/`/`pages/` del
primo avvio); se è già un vault esistente, l'app riparte da quello,
usando quel che c'è. Nessuna copia, nessun merge, nessun controllo
sul contenuto della cartella scelta — è esattamente quello che fa già
`set_vault_path` (comando M1 esistente), qui esposto in UI per la
prima volta. Resta un solo vault attivo alla volta (nessuno switcher
fra più vault, coerente col fuori-scope di SPEC.md): cambiare
percorso sostituisce quale cartella è "il vault", non ne aggiunge una
seconda.

Prima di cambiare, il frontend mostra una conferma leggera ("Apro il
vault in `<percorso>`. Procedere?"): non è un'operazione distruttiva
(niente viene copiato o cancellato), ma sostituisce comunque tutto
quello che si sta vedendo nella vista journal.

### Apri nel file manager

Accanto al bottone "Cambia" (quello che apre `pick_vault_folder`), un
bottone "Apri nel file manager" che rivela la cartella del vault
corrente in Finder (macOS) / Esplora file (Windows) / file manager di
sistema (Linux). **Nessuna dipendenza nuova**: `tauri-plugin-opener` è
già installato e registrato in questo progetto (viene dal template
Tauri di partenza), e la sua funzione `revealItemInDir` fa esattamente
questo, multipiattaforma, con un'unica chiamata JS —
`revealItemInDir(vaultPath)` da `@tauri-apps/plugin-opener`. Il
permesso `opener:default` già presente in
`src-tauri/capabilities/default.json` include già
`allow-reveal-item-in-dir`: nessuna modifica alle capability.
Nessun nuovo command Tauri: è una chiamata diretta al plugin dal
frontend, non passa da `commands.rs`.

### Bug esistente da correggere in questa spec

Il file watcher (`watcher::watch_vault`) viene creato una sola volta in
`setup()`, puntato sulla cartella del vault letta all'avvio. Cambiare
`vault_path` a runtime con `set_vault_path` lascerebbe il watcher a
osservare la cartella vecchia. Va fermato e ricreato sulla nuova
cartella subito dopo l'aggiornamento della config, dentro lo stesso
command.

### Reload della vista journal

A differenza di uno spostamento, qui la cartella nuova può avere
contenuto completamente diverso (è un vault a sé, non una copia).
Dopo un cambio riuscito il frontend deve rifare da capo il flusso di
apertura: `openToday()` + primo blocco di `listJournals`, scartando lo
stato `pages`/dirty/avvisi attuale.

Un'insidia: il path relativo del giorno corrente (es.
`journals/2026-09-09.md`) è **uguale** prima e dopo il cambio, perché
dipende solo dalla data, non dal vault. Se la key React di quella
sezione resta `page.path`, React non la smonterebbe, e l'editor
Tiptap (che carica il contenuto solo alla creazione) mostrerebbe
contenuto vecchio anche dopo il cambio vault. Serve un contatore
`vaultVersion` in `App.tsx`, incrementato a ogni cambio vault riuscito
e incluso nella key di ogni sezione (`` `${vaultVersion}:${page.path}` ``)
per forzare sempre un remount completo.

## Core (`ramus-core`)

```rust
/// Conteggio delle note nel vault: usato solo per la sezione "info" delle
/// impostazioni, non per la vista journal (che resta su list_journals
/// paginato).
pub struct VaultStats {
    pub journal_count: usize,
    pub page_count: usize,
}

pub fn stats(&self) -> Result<VaultStats, CoreError>
```

`stats`: conta i file in `journals/` che combaciano col pattern
`YYYY-MM-DD.md` (stesso filtro di `list_journals`) e i file `*.md` in
`pages/`, senza leggerne il contenuto (solo `read_dir`, niente parsing).

## Command Tauri

```
pick_vault_folder() -> Result<Option<String>, CoreError>
vault_stats() -> Result<VaultStats, CoreError>
```

Nessun nuovo command per il cambio vault: `set_vault_path` (M1,
esistente) fa già esattamente quello che serve — aggiorna la config e
chiama `ensure_exists()` sulla nuova cartella. Va solo corretto per
ricreare il file watcher dopo l'aggiornamento (vedi sopra).

- `pick_vault_folder`: apre la dialog nativa (`tauri-plugin-dialog`),
  `None` se l'utente annulla. Nessuna logica oltre alla chiamata al
  plugin: è puro I/O di sistema, non decisionale, resta ammissibile nel
  command layer.

## Tema

Nuovo campo in `Config`:

```rust
#[derive(Debug, Clone, Copy, Serialize, Deserialize, Default)]
#[serde(rename_all = "lowercase")]
pub enum Theme {
    Light,
    Dark,
    #[default]
    System,
}
```

`Config` guadagna `#[serde(default)] pub theme: Theme` — `default` è
necessario per restare compatibili con i `config.json` già scritti da
installazioni M1 che non hanno questo campo (altrimenti la
deserializzazione fallirebbe al primo avvio dopo l'aggiornamento).

Non serve un nuovo command dedicato: il tema è parte di `Config`, si
aggiorna con una piccola estensione di `set_vault_path`-style, cioè un
nuovo `set_theme(theme: Theme) -> Result<Config, CoreError>` che
aggiorna e salva solo quel campo (stesso pattern di
`Config::set_vault_path`).

### Applicazione lato frontend

`assets/palette.css` già definisce `[data-theme="dark"]` ma oggi
niente lo imposta: l'app è sempre in tema chiaro indipendentemente dal
sistema. Da correggere insieme a questa spec:

- `theme: "light"` → `document.documentElement.dataset.theme = "light"`.
- `theme: "dark"` → `"dark"`.
- `theme: "system"` → nessun attributo esplicito (si lascia decidere al
  media query `prefers-color-scheme` già presente in `palette.css` per
  il ramo dark... **verificare**: `palette.css` oggi ha solo il
  selettore `[data-theme="dark"]`, non un `@media (prefers-color-scheme:
  dark)`. Va aggiunto quel blocco media query perché "sistema" funzioni
  senza che il frontend debba leggere `matchMedia` esplicitamente.
- Applicato una volta al bootstrap (dopo `getConfig`) e su ogni cambio
  dal pannello impostazioni.

### Bug scoperto dopo l'implementazione: controlli nativi sempre chiari

`[data-theme]`/`prefers-color-scheme` in `palette.css` cambiano solo le
variabili colore usate dal nostro CSS — non toccano i controlli nativi
del browser/webview (calendario di `<input type="date">`, scrollbar,
ecc.), che seguono la proprietà CSS `color-scheme`, mai impostata. Col
tema scuro attivo il calendario del date picker in `JournalControls`
restava bianco. Corretto aggiungendo `color-scheme: light` / `dark`
accanto alle variabili colore, negli stessi tre selettori (`:root`,
la media query di sistema, `[data-theme="dark"]`).

Nota per il futuro: il popup del calendario nativo non è altrimenti
stilabile via CSS (né WebKit né Chromium lo espongono oltre
chiaro/scuro) — personalizzarlo oltre a questo richiederebbe sostituirlo
con un calendario fatto a mano, fuori scope qui.

## Info vault

Sezione read-only nel pannello: percorso vault corrente, numero di
journal, numero di pagine (da `vault_stats()`). Nessuna azione
associata, solo lettura — va rieseguita ogni volta che il pannello si
apre (i conteggi possono cambiare nel tempo).

## Frontend

- `src/components/SettingsPanel.tsx`: modale con le tre sezioni sopra,
  bottoni "Cambia" e "Apri nel file manager" affiancati nella sezione
  vault.
- Bottone ingranaggio in `app-header` che apre/chiude il pannello
  (stato locale in `App.tsx` o nel componente stesso).
- `src/lib/theme.ts`: `applyTheme(theme: Theme)` come sopra.
- `src/lib/commands.ts`: wrapper `pickVaultFolder`, `vaultStats`,
  `setTheme` (`setVaultPath` esiste già). `revealItemInDir` si importa
  direttamente da `@tauri-apps/plugin-opener` nel componente: non è un
  nostro command, non va in `commands.ts`.
- In `App.tsx`: nuovo stato `vaultVersion`, funzione che dopo un
  cambio vault riuscito lo incrementa e rifà il flusso di apertura
  (vedi "Reload della vista journal").

## Fuori scope per questa spec

- Multi-vault / vault recenti / switcher: resta vietato da SPEC.md — un
  solo vault attivo, cambiare percorso lo sostituisce.
- Dimensione batch infinite scroll configurabile: scartata in fase di
  scoping, resta fissa a 14 (vedi `2026-09-02-journal-vista-verticale.md`).
- Qualunque impostazione di git/sync, ricerca, AI: milestone successive.
